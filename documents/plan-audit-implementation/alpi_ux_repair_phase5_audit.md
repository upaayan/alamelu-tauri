### Findings

1. **[severity: HIGH]** Item A's shipping-and-import mechanism is asserted, not true: `resources/` placement does **not** ship a file with the packaged app, the Luna "precedent" is per-file and is never imported by main, and two further packaged-only failure modes are unaddressed — so the self-healing patch would be silently dead in exactly the installed app item D delivers, and no gate in the plan can catch it.
   - Where: §A — "`resources/` is already the declared home for shipped runtime assets in `electron-builder.alpi.yml` (precedent: the Luna extension), so it ships with the packaged app."
   - Reality, four legs:
     (a) **Packaging.** `electron-builder.alpi.yml` ships resources per-file: `extraResources` lists exactly `alpi-icon.png` and `alpi-luna-websocket-recovery.ts` (`:16-20`); `directories.buildResources: resources` (`:10`) is a build-input setting (icons, entitlements) and copies nothing into the app; `files:` packs only `out/**` and `package.json` (`:12-14`). The repo says so itself: "it is copied to `process.resourcesPath` via `extraResources`" (`main.ts:364`). Dropping `pi-ai-patch.mjs` into `resources/` ships nothing without a new `extraResources` entry.
     (b) **Import mechanism.** The Luna file is resolved dual-path (`main.ts:374-376`: `process.resourcesPath` packaged, `__dirname/../../resources` dev) but is handed to the **pi child** as a path — it is not a precedent for importing an ESM module from the built main process. The built main is a CJS bundle (`out/main/main.js`, no `"type":"module"`, electron-vite defaults, `electron.vite.config.mjs:15-26`). A workable recipe exists on Electron 39 (runtime-computed specifier + `/* @vite-ignore */` dynamic `import()`, which rollup's `dynamicImportInCjs` default preserves), and an alternative exists (literal import → the module is **bundled into** `out/main`, which ships via `files:` and needs no resource copy at all — but then `tsconfig.electron.json` needs `allowJs` or a declaration, and the "ships via resources/" rationale is moot). The plan states neither; the two routes have **contradictory** packaging implications, and picking wrong-by-omission is the failure.
     (c) **Path resolution in the packaged app.** The current core resolves pi via `execFileSync("which", ["pi"])` when `PI_GUI_PI_BIN` is unset (`patch-global-pi-ai.mjs:44`). A Finder-launched packaged app has a minimal PATH with no nvm shims — `which pi` fails there, so a verbatim move of the core kills the hook in the packaged app even if the module loads. Main already holds the answer: it resolves the pi bin PATH-independently and passes the realpath around (`resolveInstalledPiBin`, `main.ts:698`; the same value feeds `isPiPatchApplied` at `:853-855`, per the Phase 1-3 record). The moved core's `resolvePiAiTarget()` must accept that app-resolved bin; the `which` fallback belongs to the CLI block only.
     (d) **No packaged-layout gate.** §A's verification is a unit table over `shouldReapply` plus a dev-layout live check; §D's step 3 checks `patch-global-pi-ai --check` reports `patched`, which passes trivially today because the global pi is already patched. A packaged app whose hook fails every boot — silently, because §A mandates "failures log only" — passes every gate in the plan.
   - Recommendation (all inside A/D's existing commitments — making "it ships with the packaged app" true is not scope expansion): state the chosen mechanism in §A. If runtime-file: add the `extraResources` entry, resolve via the `main.ts:374-376` dual-path shape, note the `/* @vite-ignore */` dynamic import, and parameterize `resolvePiAiTarget(piBinRealPath)`. If bundled: say so, drop the "ships via resources/" sentence, and note the tsc implication. Either way, add one packaged-layout assertion to §D step 3 (e.g., force a stale `pi-patch-state.json` version in the installed app's user data and confirm the installed app rewrites it on launch, or assert the module file exists under the installed bundle's `Contents/Resources`) so the packaged hook is proven alive once. `smoke:alpi:candidate` (`package.json:33`) is an existing natural home if preferred.

2. **[severity: MEDIUM]** §B's compact will time out on real sessions: pi answers the `compact` command only **after** compaction completes, and the RPC client rejects requests at a 30-second default.

   - Evidence: installed handler is `const result = await session.compact(...); return success(id, "compact", result)` (`dist/modes/rpc/rpc-mode.js:411-414`) — the response carries the finished `CompactionResult` (`rpc-types.d.ts:237-242`), so a long LLM summarization pays its full wall-clock before the client hears back.
